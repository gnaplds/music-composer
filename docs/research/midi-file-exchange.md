# MIDI exchange and lossless project backup

Research date: 28 October 2026. Scope: MIDI 1.0 Standard MIDI Files (SMF) for the proposed desktop browser composer. This report supports a human decision; it does not settle export scope, choose a library, or describe a tested implementation.

**Assessment:** MIDI is suitable for exchanging playable musical events. A dependable restoration of this app's editing state needs its own defined project representation. That representation could technically be embedded in MIDI, but ordinary MIDI interchange alone does not guarantee its recovery.

**Documented capabilities.** SMF type 1 contains simultaneous tracks. Its first track holds the tempo map; named tracks can separate the three parts. Events carry delta-times; metrical timing uses ticks per quarter note. [MMA Standard MIDI Files 1.0, pp. 3–8](https://midi.org/standard-midi-files-specification)

MIDI Note On and Note Off messages identify a note number, channel, and velocity. MIDI 1.0 provides 16 channels and note numbers 0–127. A note's duration comes from its start and release events, rather than a duration field. Polyphonic playback permits several pitches at once. **Inference for this app:** chord tones can have different starts and lengths; a note can continue across a measure or chord-box boundary without being retriggered. The file need not represent a chord as one indivisible event. [MIDI Association message overview](https://midi.org/about-midi-part-3midi-messages), [message fields](https://midi.org/expanded-midi-1-0-messages-list)

Set Tempo stores integer microseconds per quarter note, so this app's fixed BPM maps to `60,000,000 / BPM`, rounded when needed. Time Signature supports a numerator and power-of-two denominator. Key Signature supports seven flats through seven sharps and major/minor. Timed events can record changes. [MMA SMF specification, pp. 9–10](https://midi.org/standard-midi-files-specification)

**Implication:** meter changes need not change the quarter-note BPM. A key-signature event describes context; it does not replace the explicit pitches in note messages. Exact timing is limited by the chosen tick grid and integer tempo value. An importer may also interpret or display supported metadata differently.

**The same-pitch overlap limit.** The detailed specification leaves the handling of repeated Note On messages for the same pitch and channel to the receiver. It may reuse a voice, allocate another, or ignore the new event. Every Note On still requires a corresponding Note Off. The ordinary messages do not contain a unique note-instance identifier. Consequently, two overlapping notes of the same pitch on one channel cannot guarantee the app's intended pairing of starts and ends across receivers. [MMA MIDI 1.0 Detailed Specification 4.2.1, p. A-4, inspected PDF copy](https://www.seriesten.org/docs/protocols/MIDI_1.0_Detailed_Specification.pdf#page=67)

**Recommendation:** use one named track and a distinct channel for each role if MIDI export is accepted. Separate channels distinguish a melody note from an equal-pitch chord or bass note, provided the receiving software preserves the channels. Separate tracks alone do not provide that distinction during playback on one shared channel. This does not solve equal-pitch overlaps within a role. Keep their exact identities and intervals in the project backup, and decide their export treatment explicitly; silently shortening notes would alter the composition.

**Custom meaning and backup.** SMF defines text, markers, and sequencer-specific metadata. Custom data can therefore be embedded, but readers may ignore unsupported metadata. These standard fields do not define this app's chord-box or Barry Harris semantics. [MMA SMF specification, pp. 7–10](https://midi.org/standard-midi-files-specification)

**Recommendation:** the lossless project backup should preserve note identities, roles, exact starts and durations, the original BPM, key/meter change positions, visual box boundaries, preferred/custom chord labels, and collection/color assignments. Those are requirements for restoration, not a proposed file schema. Text or markers may communicate useful labels to another editor, but cannot be assumed to reconstruct their box associations or analytical meaning. A MIDI file edited and saved elsewhere should not be treated as a verified project backup.

**MIDI versus audio.** MIDI describes a performance; its sound depends on the receiving instrument. It does not preserve the app's heard piano sound as a recording. Rendered audio serves listening and sharing, while losing direct access to the original editable notes and project annotations. These are different outputs with different purposes. [MIDI Association overview](https://midi.org/about-midi-part-1overview)

**Evidence limits.** The MIDI Association's official download pages were available, but their Google Drive PDF bodies were not readable through the research browser. SMF details were checked against an [indexed copy of the MMA document](https://www.scribd.com/document/914261406/RP-001-v1-0-Standard-MIDI-Files-Specification-96-1-4); the detailed MIDI document was inspected through the PDF copy above and matched to the [official edition listing](https://midi.org/midi-1-0-detailed-specification). No target editor, synthesizer, export, import, audio render, or backup restoration was tested. Actual interoperability remains a validation task.
